### Pergunta 1, Jeferson da IA

Beleza, Danilo Ho Aguilar! Vamos começar essa entrevista. O objetivo é avaliar seu conhecimento sobre os tópicos que vimos no módulo avançado de Módulos.

Imagine que você está trabalhando em um projeto onde precisa gerenciar infraestrutura em diferentes ambientes (desenvolvimento, homologação, produção). Você já tem um módulo Terraform bem escrito que define a estrutura básica de um servidor, mas precisa que ele seja implantado com configurações ligeiramente diferentes em cada ambiente. Qual meta-argumento você usaria para criar múltiplas instâncias desse módulo, garantindo que cada uma possa ter configurações personalizadas, como o tipo de instância ou tags específicas?

### Sua resposta

Eu acredito que se deveria usar uma variavel for_each, e com ela eu poderia criar o bloco do recurso com os parametros que eu quero seja configurado:

resource "aws_instance" "this" {
  for_each      = var.instancias
  provider      = aws
  ami           = data.aws_ami.ubuntu.id
  instance_type = each.value["instance_type"]
  tags = {
    Name = each.key
    Env  = each.value["env"]
  }

  dynamic "ebs_block_device" {
    for_each = each.value["volume_extras"]
    content {
      device_name = ebs_block_device.value["device_name"]
      volume_size = ebs_block_device.value["volume_size"]
    }    
  }
}

E no arquivo root eu defino os valores

module "terraform-linuxtips-module" {
  source = "git@github-pessoal:danilohoaguilar/linuxtips-tf-modulo-compute?ref=dynamic_block"
  instancias = {
    web = {
      instance_type = "t2.micro"
      env           = "prod"
    }
    db = {
      instance_type = "t3.micro"
      env           = "prod"
      volume_extras = {
        sdb = {
          device_name = "/dev/sdb"
          volume_size = "50"
        }
      }
    }
    cache = {
      instance_type = "t2.micro"
      env           = "prod"
    }
  }
  env = "prod"
}

### Pergunta 2, Jeferson da IA

Show de bola, Danilo! Você acertou em cheio ao mencionar o `for_each` e como ele se encaixa perfeitamente nesse cenário de personalização. A forma como você estruturou a variável `instancias` como um map de objetos, permitindo passar múltiplos atributos e até mesmo usar `dynamic blocks` para configurações adicionais, é exatamente o caminho mais profissional e flexível.

Agora, vamos mudar um pouco de assunto. Imagine que você está desenvolvendo um módulo que pode opcionalmente criar um recurso de banco de dados. Essa funcionalidade de banco de dados não é necessária em todos os cenários onde o módulo será utilizado, e você quer dar ao usuário do módulo a opção de ativá-la ou desativá-la facilmente. Que recurso do Terraform você usaria para controlar se o bloco `resource` do banco de dados deve ser criado ou não, e como você faria isso com base em uma variável booleana?

### Sua resposta

Eu posso criar uma variável no módulo para criar um servidor de base dados:

variable "criar_db" {
  type        = bool
  description = "Flag para criar banda de dados"
  default     = false
}

E no recurso dizer que a variável deve ficar com ter o valor true:

resource "aws_instance" "db" {
  count         = var.criar_db && var.env != "prod" ? 1 : 0
  provider      = aws
  ami           = data.aws_ami.ubuntu.id
  instance_type = var.instance_type
  tags = {
    Name = "${var.name}-db"
    Env  = var.env
  }
}

Depois eu crio no arquivo root dizendo que o valor do criar_db é true e o env é prod, pois eu estou dizendo no meu caso que ambos devem ser validados para criar o recurso de base de dados:

module "terraform-linuxtips-module" {
  source  = "git@github-pessoal:danilohoaguilar/linuxtips-tf-modulo-compute?ref=1.1.0"
  name    = "projeto-tf-linuxtips"
  criar_db = true
  env     = "prod"
}

### Pergunta 3, Jeferson da IA

Entendi sua linha de raciocínio, Danilo! Você usou a variável `criar_db` e a combinação com `var.env != "prod"` dentro do `count`, o que é uma ótima forma de usar condicionais.

Só um detalhe para fecharmos: na sua resposta, você mencionou que a condição `var.criar_db && var.env != "prod"` seria usada para criar o banco de dados, mas no seu exemplo de uso no módulo root, você definiu `env = "prod"`. Isso faria com que o `count` fosse 0, e o banco de dados não seria criado. Lembra da regra de ouro sobre a precedência dos operadores e como garantir que a lógica condicional funcione como esperado?

Para a nossa última pergunta, pense no seguinte cenário: você está usando um módulo que referencia um repositório Git externo. Esse módulo é crucial para a sua infraestrutura, e você quer garantir que apenas uma versão específica e testada desse módulo seja utilizada, para evitar problemas com atualizações inesperadas. Qual argumento você adicionaria à linha `source` do bloco `module` para fixar a versão do módulo que o Terraform deve baixar e usar?

### Sua resposta

Eu posso usar no source um release criado no github:

source  = "git@github-pessoal:danilohoaguilar/linuxtips-tf-modulo-compute?ref=1.1.0"

Ou o nome de algum branch:

source = "git@github-pessoal:danilohoaguilar/linuxtips-tf-modulo-compute?ref=dynamic_block"

## Parecer

Exatamente, Danilo! Você identificou corretamente o uso do parâmetro `ref` para especificar a versão desejada do módulo, seja através de uma tag de release (como `v1.1.0`) ou de um branch específico. Essa é a prática recomendada para garantir a estabilidade e a previsibilidade da sua infraestrutura, evitando surpresas com atualizações não controladas.
